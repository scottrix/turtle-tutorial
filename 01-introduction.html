1. Introduction & Prerequisites

What we are building

We are building Turtle OS: a 64-bit operating system for x86_64, written entirely in portable ANSI C11 (with the privileged instructions in a single assembly file, intrinsics.S), that boots via UEFI and runs in QEMU. By the end of this tutorial you will have:

  • A UEFI boot application that queries the firmware for a graphical framebuffer and a memory map
  • A kernel that takes over from UEFI, loads its own GDT, and writes to both a pixel-based console and a serial port
  • A build system that produces a FAT disk image you can boot in QEMU with a single make efi-run

No GRUB, no Multiboot2, no gnu-efi. Just your code and the firmware.

Why UEFI?

If you have read older OS dev tutorials, they probably used the legacy BIOS interface: real-mode assembly, int 0x10 for video, int 0x13 for disk reads, switching to protected mode, then to long mode. That approach has three problems in 2025:

  1. BIOS is deprecated. New machines ship with UEFI firmware only.
  2. The 16-bit real-mode–to–64-bit long-mode transition is enormously fiddly (CR0, CR4, EFER MSR, page tables, GDT, IDT…) and you have to do it all in assembly before writing a single line of C.
  3. UEFI firmware starts your code in 64-bit long mode with identity-mapped memory and a working stack. You can write real C from the very first instruction.

The trade-off is that UEFI uses the Microsoft x64 calling convention (rcx, rdx, r8, r9 for the first four arguments), not the System V AMD64 convention (rdi, rsi, rdx, rcx) that GCC and Linux use by default. We handle this with an assembly ABI translation layer — small wrapper functions that shuffle registers and allocate shadow space. No compiler-specific attributes are needed, so our code works with GCC, PCC, or any C compiler.

Why not gnu-efi?

The gnu-efi library provides EFI type definitions, a tiny startup file (crt0-efi-x86_64.o), and a self-relocator (reloc_x86_64.o in libgnuefi.a). We use none of it. We write our own type definitions in include/boot/efi.h; our own PE entry point is the _efi_entry symbol in src/boot/efi_call.S (the UEFI PE loader jumps directly to it); and we ship a tiny src/boot/efi_pe.S that provides the single thing UEFI still demands — a .reloc section.

The reason is twofold. First, gnu-efi's self-relocator walks the .rela section at runtime and patches up absolute addresses; in larger binaries we observed it corrupting function pointers. Second, with -fpic -shared -Bsymbolic the linker resolves every symbol reference at link time, so readelf -r on our turtle.elf reports zero relocations. The gnu-efi relocator would have nothing to do.

The UEFI PE loader expects every boot application to carry a .reloc directory entry; an image without one is rejected. Our efi_pe.S emits a single 12-byte block of two IMAGE_REL_ABSOLUTE (type 0) fixups, which the PE loader treats as no-ops. The contract is satisfied, no runtime patching is required, and we drop a distro-specific dependency.

Knowledge

  • ANSI C — pointers, structs, bitwise operators, the preprocessor. We use only portable C11 features (_Alignas, #pragma pack, ); no GCC-specific extensions.
  • x86 assembly basics — you should know what registers are, what mov, push, call, and ret do. You do not need to know 64-bit specifics; we explain those.
  • Basic Unix command line — running make, reading error messages.

The two most important files are src/boot/efi_main.c (the UEFI entry point that does all the firmware negotiation) and include/boot/efi.h (our own EFI type definitions). The kernel side — main.c, gdt.c, fb.c, printk.c — is what runs after we have exited UEFI boot services and are on our own.

A note on freestanding C

We compile every file with -ffreestanding -nostdlib -nostdinc. This means:

  • No stdio.h, no stdlib.h, no string.h from the C library
  • No main() signature enforced by the compiler — our entry point is efi_main, called by UEFI firmware
  • We must provide our own memset, memcpy, strlen, etc.
  • We use the freestanding header for variadic arguments in printk. C11 requires every freestanding implementation to provide it; GCC and PCC both ship an intrinsic copy that lives in the compiler's private include directory, so -nostdinc does not remove it.

We also use a couple of C11 standard facilities in place of the compiler-specific extensions you often see in OS tutorials:

  • #pragma pack(push, 1) / #pragma pack(pop) — removes padding from structs that must match hardware or firmware layouts. This pragma is supported by GCC, Clang, PCC, and MSVC, unlike the __attribute__((packed)) GCC extension.
  • _Alignas(N) — the C11 standard alignment specifier, used for page tables and the kernel stack. It replaces __attribute__((aligned(N))).

Inline assembly — things like cli, hlt, inb, outb, reading and writing control registers — is inherently compiler-specific. Rather than sprinkling __asm__ volatile(...) blocks through the C sources, we collect every privileged instruction into a single assembly file, src/arch/x86_64/intrinsics.S, exposing plain C functions like cpu_cli(), inb(port), and read_cr3(). The C compiler only ever sees normal function calls; it never has to know about extended-asm syntax. This is the same trick we already use for the UEFI ABI bridge in efi_call.S.

The net result is that all of our C code is portable ANSI C11. The only compiler-specific knowledge lives in those two .S files — and they only require an x86 assembler, not a particular C compiler. We have built and tested with GCC; PCC needs only the assembly constraint fixes detailed in Chapter 16.

Notably, we do not use __attribute__((ms_abi)) anywhere in our C code. The UEFI calling convention is handled entirely by the assembly ABI translation layer in efi_call.S (see Chapter 16). This makes the OS compilable with PCC, which lacks the ms_abi extension.
