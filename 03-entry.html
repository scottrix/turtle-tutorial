3. The Boot Entry Point & ABI Bridge

How UEFI calls our code

When the UEFI firmware loads BOOTX64.EFI, it calls the PE entry point with two arguments:

  • ImageHandle (in rcx) — a handle representing our loaded image
  • SystemTable (in rdx) — a pointer to the EFI_SYSTEM_TABLE

These arrive via the Microsoft x64 calling convention (rcx, rdx, r8, r9). But our C code, compiled with GCC or PCC, expects the System V AMD64 convention (rdi, rsi, rdx, rcx). We need a bridge.

The entry point: _efi_entry

Our bridge is in assembly, in src/boot/efi_call.S. The linker script sets ENTRY(_efi_entry), so the PE header points to this function. It receives the UEFI call (MS ABI), translates the registers to SysV ABI, and calls our C efi_main: 

.global _efi_entry
_efi_entry:
	mov %rcx, %rdi        /* ImageHandle: RCX → RDI */
	mov %rdx, %rsi        /* SystemTable: RDX → RSI */
	sub $0x28, %rsp       /* shadow space for efi_main */
	call efi_main
	add $0x28, %rsp
	ret

The gnu-efi crt0-efi-x86_64.o startup code receives the initial UEFI call, does some housekeeping (stack setup, relocation), and then calls _efi_entry using the MS ABI. Our _efi_entry translates to SysV ABI and calls efi_main.

Why not just use __attribute__((ms_abi))?

In earlier versions of this project, we used GCC's __attribute__((ms_abi)) to make efi_main use the MS ABI directly. GCC then generated the register shuffling code automatically for every UEFI function call. This worked, but it created a dependency on a GCC-specific extension.

We want our OS to be compilable with PCC (Portable C Compiler), which does not support __attribute__((ms_abi)). By moving all ABI translation into assembly wrappers (efi_call0 through efi_call6), no C code needs any compiler-specific ABI annotations.

The ABI translation layer is covered in detail in Chapter 16. For now, the key idea is: no C function in our codebase uses EFIAPI or __attribute__((ms_abi)). All ABI translation happens in efi_call.S.

What about the stack?

UEFI firmware sets up a stack for us before calling the entry point. The gnu-efi crt0 code allocates an additional 64KB of stack space and aligns it to 16 bytes. We don't need to do anything special — we can use local variables, function calls, and recursion normally.

The flow, visualized

UEFI firmware
  |
  | (MS ABI: rcx=ImageHandle, rdx=SystemTable)
  v
crt0-efi-x86_64.o (gnu-efi startup)
  |
  | (MS ABI: rcx=ImageHandle, rdx=SystemTable)
  v
_efi_entry() in efi_call.S
  |
  | (translates to SysV ABI: rdi=ImageHandle, rsi=SystemTable)
  v
efi_main() in efi_main.c [plain C, no EFIAPI]
  |
  | (calls efi_call2(g_BS->GetMemoryMap, ...) etc.)
  v
efi_call5() in efi_call.S
  |
  | (translates back to MS ABI: rcx, rdx, r8, r9, stack)
  v
UEFI boot services (GetMemoryMap, ExitBootServices, etc.)

The key insight: all ABI translation is in one file (efi_call.S). No C code needs to know about the Microsoft calling convention. The compiler can be GCC, PCC, or any compiler that supports the System V AMD64 ABI.
