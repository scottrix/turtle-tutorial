3. The Boot Entry Point & ABI Bridge

How UEFI calls our code

When the UEFI firmware loads BOOTX64.EFI, it calls the PE entry point with two arguments:

  • ImageHandle (in rcx) — a handle representing our loaded image
  • SystemTable (in rdx) — a pointer to the EFI_SYSTEM_TABLE

These arrive via the Microsoft x64 calling convention (rcx, rdx, r8, r9). But our C code, compiled with GCC, expects the System V AMD64 convention (rdi, rsi, rdx, rcx). We need a bridge.

The entry point: entry.c

Our bridge is deliberately simple. The gnu-efi crt0-efi-x86_64.o startup code receives the UEFI call (using the MS ABI), then calls our _entry function. Our _entry just forwards to efi_main: 

#include <boot/efi.h>

extern EFI_STATUS EFIAPI efi_main(EFI_HANDLE ImageHandle,
                                   EFI_SYSTEM_TABLE *SystemTable);

void _entry(EFI_HANDLE ImageHandle, EFI_SYSTEM_TABLE *SystemTable)
{
    efi_main(ImageHandle, SystemTable);
}

Wait — _entry is compiled with the System V ABI (because GCC defaults to it), but it's called from the MS-ABI crt0 startup code. How does this work?

The gnu-efi crt0-efi-x86_64.o does the argument shuffling for us. It receives (rcx=ImageHandle, rdx=SystemTable), then moves them to (rdi, rsi) before calling our _entry. So by the time _entry runs, the arguments are already in System V registers.

Then _entry calls efi_main, which is declared with EFIAPI (= __attribute__((ms_abi))). GCC automatically generates the code to shuffle (rdi, rsi) back to (rcx, rdx) for that call. The compiler handles all the ABI translation.

Why EFIAPI on efi_main?

You might wonder: if _entry is SYSV ABI, and it calls efi_main, why does efi_main need to be MS ABI?

Because efi_main calls UEFI boot services (g_BS->GetMemoryMap, etc.), and those function pointers expect to be called with the MS ABI. If efi_main itself were SYSV ABI, then every time it called a boot service function pointer, it would need an explicit assembly shim. By making efi_main MS ABI, GCC handles the convention automatically for all calls inside it.

In practice, the simplest approach is: make efi_main and every function it calls that touches UEFI APIs use EFIAPI. Functions that are pure C (no UEFI calls) can stay SYSV ABI. Our entry.c bridge is just a one-line forwarder.

What about the stack?

UEFI firmware sets up a stack for us before calling the entry point. The gnu-efi crt0 code allocates an additional 64KB of stack space and aligns it to 16 bytes. We don't need to do anything special — we can use local variables, function calls, and recursion normally.

The flow, visualized

UEFI firmware
    |
    | (MS ABI: rcx=ImageHandle, rdx=SystemTable)
    v
crt0-efi-x86_64.o (gnu-efi startup)
    |
    | (shuffles to SYSV ABI: rdi=ImageHandle, rsi=SystemTable)
    v
_entry() in entry.c
    |
    | (GCC auto-shuffles back to MS ABI: rcx, rdx)
    v
efi_main() in efi_main.c    [EFIAPI = __attribute__((ms_abi))]
    |
    | (MS ABI function pointers in BootServices)
    v
UEFI boot services (GetMemoryMap, ExitBootServices, etc.)

The key insight: the compiler does the heavy lifting. We just need the EFIAPI annotation on the right functions, and GCC generates all the register shuffling code.
