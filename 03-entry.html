3. The Boot Entry Point & ABI Bridge

How UEFI calls our code

When the UEFI firmware loads BOOTX64.EFI, it calls the PE entry point with two arguments:

  • ImageHandle (in rcx) — a handle representing our loaded image
  • SystemTable (in rdx) — a pointer to the EFI_SYSTEM_TABLE

These arrive via the Microsoft x64 calling convention (rcx, rdx, r8, r9). But our C code, compiled with GCC or PCC, expects the System V AMD64 convention (rdi, rsi, rdx, rcx). We need a bridge.

The entry point: _efi_entry

Our bridge is in assembly, in src/boot/efi_call.S. The linker script sets ENTRY(_efi_entry), so the PE header points to this function. It receives the UEFI call (MS ABI), translates the registers to SysV ABI, and calls our C efi_main: 

.global _efi_entry
_efi_entry:
	mov %rcx, %rdi        /* ImageHandle: RCX → RDI */
	mov %rdx, %rsi        /* SystemTable: RDX → RSI */
	sub $0x28, %rsp       /* shadow space for efi_main */
	call efi_main
	add $0x28, %rsp
	ret

The UEFI PE loader reads the AddressOfEntryPoint field from our PE header and jumps directly to _efi_entry in efi_call.S using the MS ABI. Our _efi_entry translates registers to the SysV ABI and calls efi_main. There is no gnu-efi startup file in the chain — the firmware's PE loader is the only thing that runs before our code. The same assembly file provides efi_call0 through efi_call6 wrappers for every UEFI boot-services call we make, so no C function in the codebase needs EFIAPI or __attribute__((ms_abi)). The full ABI translation layer is covered in Chapter 16.

What about the stack?

UEFI firmware sets up a stack for us before calling the entry point and aligns it to 16 bytes per the MS ABI. We don't need to do anything special — we can use local variables, function calls, and recursion normally. (Later, after ExitBootServices, we switch to our own kernel stack; see Chapter 14.)

The flow, visualized

UEFI firmware (PE loader)
  |
  | (loads turtle.efi, jumps to AddressOfEntryPoint)
  | (MS ABI: rcx=ImageHandle, rdx=SystemTable)
  v
_efi_entry() in efi_call.S
  |
  | (translates to SysV ABI: rdi=ImageHandle, rsi=SystemTable)
  v
efi_main() in efi_main.c [plain C, no EFIAPI]
  |
  | (calls efi_call2(g_BS->GetMemoryMap, ...) etc.)
  v
efi_call5() in efi_call.S
  |
  | (translates back to MS ABI: rcx, rdx, r8, r9, stack)
  v
UEFI boot services (GetMemoryMap, ExitBootServices, etc.)

The key insight: all ABI translation is in one file (efi_call.S). The UEFI PE loader jumps directly to _efi_entry — there is no gnu-efi startup file in the chain. No C code needs to know about the Microsoft calling convention. The compiler can be GCC, PCC, or any compiler that supports the System V AMD64 ABI.
