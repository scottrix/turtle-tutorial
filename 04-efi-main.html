4. EFI Main: The UEFI Boot Phase

This chapter covers the first half of efi_main(): saving the system table pointer, printing to the UEFI console, disabling the watchdog timer, and the overall life cycle of a UEFI boot application. The second half (GOP, memory map, ExitBootServices) is covered in Chapters 5 and 6.

efi_main signature

EFI_STATUS EFIAPI efi_main(EFI_HANDLE ImageHandle,
                            EFI_SYSTEM_TABLE *SystemTable)
{

EFIAPI ensures the Microsoft x64 calling convention. ImageHandle is our loaded image handle (needed later for ExitBootServices and OpenProtocol). SystemTable is the master table with pointers to everything UEFI provides.

Saving the table pointers

static EFI_SYSTEM_TABLE *g_ST;
static EFI_BOOT_SERVICES *g_BS;

g_ST = SystemTable;
g_BS = SystemTable->BootServices;

We save these as file-scope statics because every UEFI call needs one or the other. g_ST gives us console output and the configuration table; g_BS gives us memory allocation, protocol lookup, and ExitBootServices.

Printing to the UEFI console

UEFI's console output uses 16-bit characters (CHAR16). Our helper converts ASCII to CHAR16: 

static void print(const char *s)
{
    CHAR16 buf[256];
    int i;
    for (i = 0; s[i] && i < 255; i++)
        buf[i] = (CHAR16)s[i];
    buf[i] = 0;
    g_ST->ConOut->OutputString(g_ST->ConOut, buf);
}

OutputString is a function pointer in the ConOut protocol. The first argument is always This — a pointer to the protocol instance itself (UEFI uses a C++-like OOP pattern).

We also have hex and decimal printing helpers: 

static void print_hex(uint64_t val)
{
    const char hex[] = "0123456789ABCDEF";
    char buf[17];
    int i = 0;
    if (val == 0) { print("0"); return; }
    char tmp[16];
    int j = 0;
    while (val) {
        tmp[j++] = hex[val & 0xF];
        val >>= 4;
    }
    while (--j >= 0)
        buf[i++] = tmp[j];
    buf[i] = '\0';
    print(buf);
}

These are simple, but they let us print status messages during boot, which is invaluable for debugging. Once we exit boot services, these functions stop working (because ConOut is a boot service). We switch to serial output at that point (Chapter 8).

Clearing the screen

g_ST->ConOut->ClearScreen(g_ST->ConOut);

This clears the UEFI console and resets the cursor. It's cosmetic but makes our output easier to read.

The watchdog timer

g_BS->SetWatchdogTimer(0, 0, 0, NULL);

UEFI firmware sets a 5-minute watchdog timer on boot applications. If the timer expires, the firmware resets the machine. This is a safety mechanism: if your bootloader hangs, the system reboots instead of staying frozen forever.

We disable it by setting the timeout to 0. This is important because our kernel will eventually sit in an infinite loop (the idle loop), and we don't want the firmware to reboot us.

The boot life cycle

A UEFI boot application goes through these phases:

  1. Boot services active — can call any function in EFI_BOOT_SERVICES (console output, memory allocation, protocol lookup, etc.)
  2. Get memory map — must be done immediately before exiting boot services, because any boot service call changes the map
  3. ExitBootServices — tells the firmware we're done. After this, no boot service calls are allowed. Console output, memory allocation, and protocol access all become invalid.
  4. Kernel mode — we're on our own. We have the memory map, the framebuffer address, and raw hardware access.

The transition from step 3 to step 4 is the most critical moment in the boot. Once we call ExitBootServices, we can never go back. We must have gathered all the information we need before that call.

What we gather before exiting

  • Framebuffer info — base address, size, resolution, pixel format (via GOP, Chapter 5)
  • Memory map — which memory regions are available, reserved, or MMIO (Chapter 6)
  • RSDP address — the ACPI table pointer (for future use; hardware enumeration)

All of this goes into a struct boot_info that we pass to kernel_main().

The boot_info structure

struct boot_info {
    struct framebuffer_info fb;
    uint64_t rsdp_addr;
    uint64_t kernel_virtual_base;
    uint64_t kernel_physical_base;
    uint64_t kernel_size;
    uint64_t total_memory;
    uint32_t num_memory_map_entries;
    uint32_t reserved;
};

The kernel_virtual_base, kernel_physical_base, and kernel_size fields are for when we set up higher-half kernel addressing in the future. For now they're zero.
