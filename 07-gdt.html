7. The GDT in 64-bit Long Mode

After exiting UEFI boot services, the firmware's GDT is still loaded. We need our own so we can control segment selectors and set up a TSS (Task State Segment) for future interrupt handling. This chapter explains how the GDT works in 64-bit long mode and why the entries are different from 32-bit protected mode.

What is the GDT?

The Global Descriptor Table (GDT) is a data structure that the CPU uses to translate segment selectors (values in segment registers like CS, DS, SS) into segment descriptors. Each descriptor defines a memory segment's base address, limit, access rights, and granularity.

In 32-bit protected mode, the GDT matters a lot: segments can have different base addresses and limits, and the CPU enforces access rights. In 64-bit long mode, most of this is ignored:

  • Base address is always 0 — CS, DS, ES, SS all start at address 0 in long mode. The hardware ignores the base field.
  • Limit is ignored — all segments cover the entire 64-bit address space.
  • Access rights still matter — the CPU checks whether a segment is present, readable/writable, and whether it's code or data. A wrong access byte will cause a general protection fault.
  • The L bit matters — this is the 64-bit flag. Setting L=1 and D=0 in a code descriptor means "this is a 64-bit code segment".

So why do we still need a GDT? Two reasons:

  1. The CPU requires valid descriptors in CS and SS. If we load a null descriptor into CS, we triple-fault immediately.
  2. We need a TSS descriptor for the Task State Segment. The TSS holds stack pointers for privilege level changes (e.g., when an interrupt fires while running in user mode, the CPU switches to the kernel stack defined in the TSS).

GDT entry layout

Each GDT entry is 8 bytes (64 bits). In 64-bit mode, a TSS descriptor takes 16 bytes (two entries). Here's the bit layout of a standard 8-byte descriptor: 

 31..24  | 23..22 | 21 | 20..19 | 15..14 | 13 | 12..8 | 7..0
---------|--------|----|--------|--------|----|-------|------
Base[31:24] | G | D/L |  AVL  | Limit[19:16] | P | DPL | S | Type
            |   |     |       |              |   |     |   |
            |   |     |       |              |   |     |   +-- 4 bits
            |   |     |       |              |   +-----+------ 4 bits
            |   |     |       |              +-------------------- 1 bit
            |   |     |       +----------------------------------- 4 bits
            |   |     +------------------------------------------- 1 bit
            |   +------------------------------------------------- 1 bit
            +----------------------------------------------------- 1 bit

Low 32 bits:
 31..16        | 15..0
---------------|-------
Base[23:16]    | Limit[15:0]

The 64-bit code descriptor

For a 64-bit code segment (the one CS must point to), the key fields are:

FieldValueWhy
Type0xA (Execute/Read)Code segments must be executable
S1Code/data descriptor (not a system segment)
DPL0 (ring 0) for kernel, 3 for userPrivilege level
P1Segment is present
L164-bit mode
D0Must be 0 when L=1 (CPU requirement)
G1Granularity: limit is in 4K pages

The access byte for a kernel 64-bit code segment is: 

P DPL S Type
1 00  1 1010  = 0x9A

The granularity byte: 

G D  L  AVL Limit[19:16]
1 0  1  0    1111         = 0xAF
The L bit (0x20 in the granularity byte) is what makes this a 64-bit descriptor. Without it, the CPU treats the code segment as 32-bit and everything goes wrong. The granularity byte must be 0xAF, not 0x4F (which would be a 32-bit code segment with L=0).

The data descriptor

Data segments are simpler. In 64-bit long mode, the CPU ignores the base and limit for data segments, but we still need valid descriptors in DS, ES, FS, GS, and SS: 

Access:     1 00 1 0010 = 0x92  (Read/Write data, ring 0)
Granularity: 1 1 0 0 1111 = 0xCF  (G=1, D/B=1, L=0, limit=0xFFFFF)

For the data segment, D/B=1 (the "B" bit for data segments) and L=0 (64-bit code segments use L; data segments don't have an L bit).

We originally used 0xA for code granularity and 0xC for data granularity. These set G=1 and Limit=0xF but had wrong L/D bits. The code descriptor had L=0 (32-bit!), causing a triple fault on lretq. The correct values are 0xAF for 64-bit code and 0xCF for data. This is the kind of bug that gives OS development its reputation.

Our GDT layout

Index | Selector | Description
------+----------+------------------------------------------
  0   |   0x00   | Null descriptor (required by CPU)
  1   |   0x08   | 64-bit kernel code (ring 0)
  2   |   0x10   | Kernel data (ring 0)
  3   |   0x18   | 64-bit user code (ring 3)
  4   |   0x20   | User data (ring 3)
  5-6 |   0x28   | TSS descriptor (16 bytes, two entries)

Selectors are index × 8 (since each entry is 8 bytes). The TSS at index 5 uses selector 0x28.

The TSS in 64-bit mode

The 64-bit TSS structure is different from the 32-bit one. It has three stack pointers (RSP0, RSP1, RSP2) for privilege-level changes, seven IST (Interrupt Stack Table) pointers, and an I/O bitmap offset: 

#pragma pack(push, 1)
struct tss_entry {
    uint32_t reserved0;
    uint64_t rsp[3];     /* RSP0, RSP1, RSP2 */
    uint64_t reserved1;
    uint64_t ist[7];     /* IST1..IST7 */
    uint64_t reserved2;
    uint16_t reserved3;
    uint16_t iomap_base;
};
#pragma pack(pop)

RSP0 is the most important field: when the CPU receives an interrupt while running at ring 3, it switches to RSP0 before calling the interrupt handler. We'll set this to our kernel stack address when we implement interrupt handling.

iomap_base must be set to sizeof(struct tss_entry) (104) to indicate "no I/O bitmap" (any value ≥ 104 disables the I/O permission bitmap).

Setting up the TSS descriptor

In 64-bit mode, a TSS descriptor is 16 bytes (two GDT entries). The lower 8 bytes look like a standard descriptor with type=0x89 (64-bit TSS, busy=0). The upper 8 bytes contain the upper 32 bits of the TSS base address: 

static void tss_set_descriptor(int idx, uint64_t base, uint64_t limit)
{
    uint32_t base_low  = (uint32_t)(base & 0xFFFFFFFF);
    uint32_t base_high = (uint32_t)(base >> 32);

    gdt[idx].limit_low   = (uint16_t)(limit & 0xFFFF);
    gdt[idx].base_low    = (uint16_t)(base_low & 0xFFFF);
    gdt[idx].base_mid    = (uint8_t)((base_low >> 16) & 0xFF);
    gdt[idx].access      = 0x89;   /* 64-bit TSS, present */
    gdt[idx].granularity = 0x00;
    gdt[idx].base_high   = (uint8_t)((base_low >> 24) & 0xFF);

    gdt[idx + 1].limit_low = (uint16_t)(base_high & 0xFFFF);
    /* remaining bytes zero */
}

Initializing the GDT

void gdt_init(void)
{
    memset(&tss, 0, sizeof(struct tss_entry));
    tss.rsp[0] = 0;                        /* set later with kernel stack */
    tss.iomap_base = sizeof(struct tss_entry);

    gdt_set_entry(0, 0, 0, 0, 0);                      /* null */
    gdt_set_entry(1, 0, 0xFFFFF, 0x9A, 0xAF);          /* kernel code */
    gdt_set_entry(2, 0, 0xFFFFF, 0x92, 0xCF);          /* kernel data */
    gdt_set_entry(3, 0, 0xFFFFF, 0xFA, 0xAF);          /* user code */
    gdt_set_entry(4, 0, 0xFFFFF, 0xF2, 0xCF);          /* user data */
    tss_set_descriptor(5, (uint64_t)&tss,
                       sizeof(struct tss_entry) - 1);

    gdt_pointer.limit = sizeof(gdt) - 1;
    gdt_pointer.base  = (uint64_t)&gdt;
}

Loading the GDT

This is the most delicate operation. We need to:

  1. Load the new GDT with lgdt
  2. Reload all data segment registers with our new data selector (0x10)
  3. Far-jump to our new code selector (0x08) using lretq
  4. Load the task register with our TSS selector (0x28)
void gdt_load(void)
{
    gdt_load_asm(&gdt_pointer);
}

The actual lgdt + segment reload lives in src/arch/x86_64/intrinsics.S as gdt_load_asm. Keeping it in assembly means the C compiler never sees the position-sensitive lea 1f(%rip) addressing or the lretq far-return trick; the C side is just an ordinary function call.

The body of gdt_load_asm does the four steps above:

  1. lgdt (%rdi) — load the new GDT (the pointer was passed in rdi per the SysV ABI).
  2. Reload ds, es, fs, gs, ss with 0x10 (our data selector).
  3. Far-jump to 0x08 using lretq: push the new CS selector, push the address of the next instruction (lea 1f(%rip)), then do a far return. This atomically reloads CS and continues execution. lea 1f(%rip) computes the address relative to the current instruction pointer, which works regardless of where the kernel is loaded.
  4. ltr $0x28 — load the task register with our TSS selector.
The clobber list must use "rax", not "ax". In 64-bit mode, the register is RAX. Some compilers (like PCC) only accept the full-size name. GCC accepts both, but "rax" is more portable.
