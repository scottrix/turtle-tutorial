8. Kernel Main & Serial I/O

After ExitBootServices and the GDT load, we're in bare-metal 64-bit long mode with our own segment descriptors. Now we call kernel_main() — the first "real" kernel function. But there's a catch: the UEFI console is gone, so we need our own output mechanism. That's where the serial port comes in.

The serial port: COM1 at I/O port 0x3F8

The PC's first serial port (COM1) lives at I/O port address 0x3F8. In 64-bit long mode, we access I/O ports using the outb and inb instructions:

  • outb data, port — write a byte to an I/O port
  • inb port, reg — read a byte from an I/O port

In GCC inline assembly: 

static void serial_out(char c)
{
    __asm__ volatile("outb %0, %1"
                     : : "a"(c), "Nd"((uint16_t)0x3F8));
}

The constraint "a" puts the character in AL (low byte of RAX). The constraint "Nd" puts the port number in a register or as an immediate (the N modifier means "0..255 immediate", and d means "any general register"). Since 0x3F8 fits in 16 bits, the assembler can use the shorter outb %al, $0x3F8 encoding.

Why not memory-mapped I/O?

You might be tempted to write to the UART's memory-mapped address: 

volatile uint8_t *com1 = (volatile uint8_t *)0x3F8;
com1[0] = 'H';  /* WRONG after EBS! */
This causes a page fault after ExitBootServices. UEFI's page tables map the UART's MMIO address during boot services, but after EBS, those mappings may no longer be present (or the firmware may have used a different virtual address). Address 0x3F8 as a memory address is not the same as I/O port 0x3F8. The I/O port space is separate and accessed via in/out instructions, not memory reads/writes.

Why the delay loop?

static void serial_puts(const char *s)
{
    while (*s) {
        serial_out(*s++);
        for (volatile int i = 0; i < 400; i++)
            ;
    }
}

In real hardware, you should check the UART's Line Status Register (bit 5 = Transmitter Holding Register Empty) before sending each byte: 

/* Correct approach for real hardware: */
while (!(inb(0x3FD) & 0x20))  /* wait for THR empty */
    ;
outb(c, 0x3F8);

However, in QEMU, the emulated UART's THR-empty bit never becomes set (at least not in a timely manner), so polling loops hang forever. The delay loop is a pragmatic workaround: we burn a few hundred CPU cycles between characters, which is enough for QEMU's emulated UART to process each byte.

For production, you'd implement proper UART initialization (set baud rate, enable FIFOs, configure interrupts) and check the LSR. The delay loop is a development convenience.

kernel_main

void kernel_main(struct boot_info *info)
{
    serial_puts("Turtle OS kernel_main reached!\n");

    if (info && info->fb.base_addr) {
        fb_init(&info->fb);
        printk("Turtle OS v0.1\n");
        printk("64-bit POSIX-compatible kernel\n\n");
        printk("Framebuffer: %dx%d %d bpp\n",
               info->fb.width, info->fb.height, info->fb.bpp);
        printk("Total memory: %lu MB\n",
               info->total_memory / (1024 * 1024));
    }

    serial_puts("Kernel initialized.\n");

    for (;;)
        __asm__ volatile("cli; hlt");
}

The function does three things:

  1. Serial output — serial_puts confirms we reached kernel_main. This is our most reliable debug channel: it works even without a framebuffer.
  2. Framebuffer initialization — fb_init sets up the graphical console (Chapter 9), and printk prints formatted text to it.
  3. Halt loop — cli; hlt disables interrupts and halts the CPU. If an NMI arrives, the for(;;) loop re-halts. This is the idle loop: the kernel just sits here until we implement scheduling.

Why two output channels?

Having both serial and framebuffer output is extremely useful:

  • Serial works from the very first instruction after EBS. It's simple, reliable, and you can capture it to a file with QEMU's -serial stdio or -serial file:log.txt.
  • Framebuffer shows text on the QEMU window. It's what a user would see on a real machine. But it requires the GOP information, font data, and a working fb_init.

If the framebuffer fails, serial still works. If QEMU's serial output is misconfigured, the screen still works. Redundancy is your friend when debugging boot code.
