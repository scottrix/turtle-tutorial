10. The Build System

Building a UEFI boot application is different from building a normal executable. The output must be a PE+ (Portable Executable 64-bit) file, not an ELF binary. The UEFI PE loader doesn't understand ELF. We use a two-step process: link as ELF, then convert to PE.

Compiler flags

Every file — boot code and kernel code alike — is compiled with one set of flags, producing a position-independent freestanding binary:

EFI flags

EFI_CFLAGS = -ffreestanding -fshort-wchar -fpic -fno-stack-protector \
             -fno-lto -fno-exceptions -fno-unwind-tables \
             -fno-asynchronous-unwind-tables \
             -mno-red-zone -mno-mmx -mno-sse -mno-sse2 \
             -Wall -Wextra -std=c11 -O2 -Iinclude
  • -fshort-wchar — makes wchar_t 2 bytes (UEFI uses CHAR16, and L"string" literals must produce 2-byte characters)
  • -fpic — position-independent code. UEFI loads our image at a dynamic address and the relocator patches up GOT-relative references. Without -fpic, we'd get absolute relocations that the PE loader can't handle.
  • -mno-red-zone — the x86_64 red zone (128 bytes below RSP that signal handlers won't clobber) is not safe in a kernel or bootloader. Interrupts can fire at any time and overwrite it.
  • -mno-mmx -mno-sse -mno-sse2 — UEFI firmware may not have set up SSE. We avoid all SSE instructions so the compiler doesn't generate them.

The EFI linker script

efi_linker.ld defines the section layout: 

OUTPUT_FORMAT(elf64-x86-64)
ENTRY(efi_main)

SECTIONS
{
    . = 0;
    ImageBase = .;
    .hash : { *(.hash) }
    .gnu.hash : { *(.gnu.hash) }
    . = ALIGN(4096);
    .text : { *(.text) *(.text.*) . = ALIGN(16); }
    . = ALIGN(4096);
    .rodata : { *(.rodata) *(.rodata.*) }
    . = ALIGN(4096);
    .data : {
        *(.got.plt) *(.got) *(.data) *(.data.*)
        *(.sdata) *(.sbss) *(.scommon) *(.dynbss)
        *(.bss) *(.bss.*) *(COMMON)
    }
    . = ALIGN(4096);
    .reloc : { KEEP (*(.reloc)) }
    . = ALIGN(4096);
    .dynamic : { *(.dynamic) }
    . = ALIGN(4096);
    .rela : { *(.rela.text*) *(.rela.data*) *(.rela.got) *(.rela.dyn) }
    /* ... more sections ... */
    /DISCARD/ : { *(.comment) *(.note.*) *(.eh_frame) }
}

Key points:

  • ImageBase = 0 — the image is relocatable; the actual load address is determined by UEFI
  • Sections are 4096-byte aligned — UEFI expects page-aligned sections
  • .reloc is kept — this is the PE relocation section that the UEFI loader uses
  • .eh_frame is discarded — we don't use C++ exception handling or stack unwinding

Linking

EFI_LDFLAGS = -nostdlib -z noexecstack -shared -Bsymbolic \
              -T efi_linker.ld \
              /usr/lib/crt0-efi-x86_64.o \
              /usr/lib/libgnuefi.a

ld $(EFI_LDFLAGS) -o build/turtle.elf $(EFI_OBJS)
  • -shared — produce a shared library (ET_DYN), which is what UEFI expects
  • -Bsymbolic — resolve all symbol references within the binary at link time, reducing the number of relocations the gnu-efi relocator needs to fix up
  • crt0-efi-x86_64.o — gnu-efi startup code (handles the PE entry point, stack allocation, and calling our _entry)
  • libgnuefi.a — contains reloc_x86_64.o, the self-relocator that patches .rela entries at runtime

ELF to PE conversion

objcopy -I elf64-x86-64 -O pei-x86-64 \
    -j .text -j .sdata -j .data -j .dynamic \
    -j .dynsym -j .rela -j .rela.* -j .reloc \
    -j .rodata -j .rodata.* \
    --subsystem=10 \
    build/turtle.elf build/turtle.efi

--subsystem=10 is the EFI subsystem ID. This tells the UEFI loader that this is a boot application. The -j flags select only the sections we want (excluding debug info, comments, etc.).

Creating the disk image

UEFI boots from a FAT32 filesystem. We create a 4MB image, format it, and copy our EFI binary to the expected path: 

dd if=/dev/zero of=build/turtle.img bs=1M count=4
mkfs.vfat build/turtle.img
mmd -i build/turtle.img ::EFI ::EFI/BOOT
mcopy -i build/turtle.img build/turtle.efi ::EFI/BOOT/BOOTX64.EFI

The path \EFI\BOOT\BOOTX64.EFI is the UEFI fallback boot path — any UEFI firmware will look for this file on a FAT partition and load it if no other boot entry is configured.

Running in QEMU

qemu-system-x86_64 \
    -drive if=pflash,format=raw,readonly=on,file=/usr/share/edk2/x64/OVMF_CODE.4m.fd \
    -drive if=pflash,format=raw,file=/tmp/OVMF_VARS.4m.fd \
    -drive if=virtio,format=raw,file=build/turtle.img \
    -m 128M -net none -serial stdio -vga std -no-reboot

Breaking down the QEMU flags:

  • -drive if=pflash,...,file=OVMF_CODE.4m.fd — the UEFI firmware code (read-only). This is OVMF, the open-source UEFI implementation from the TianoCore project.
  • -drive if=pflash,...,file=OVMF_VARS.4m.fd — the UEFI variable store (writable). This stores boot configuration. We copy a fresh copy each run to avoid stale state.
  • -drive if=virtio,...,file=turtle.img — our disk image. Using virtio for better performance than IDE.
  • -m 128M — 128MB of RAM (plenty for our kernel)
  • -serial stdio — redirect the first serial port (COM1) to the terminal. This is how we see serial output.
  • -vga std — standard VGA, which enables the GOP framebuffer in OVMF
  • -no-reboot — exit QEMU instead of rebooting on a triple fault (useful for debugging)

The full build flow

make efi-run

# This runs the following steps:
#
# 1. Compile each .c file with gcc (EFI_CFLAGS)
# 2. Convert font.bin to font.o with objcopy
# 3. Link all .o files with ld + crt0-efi + libgnuefi.a
# 4. Convert turtle.elf to turtle.efi with objcopy
# 5. Create turtle.img (FAT filesystem with BOOTX64.EFI)
# 6. Copy fresh OVMF_VARS
# 7. Launch QEMU

If everything works, you should see: 

Turtle OS v0.1 (UEFI)
GOP: 1280x800 @ 0x80000000
Memory: 121 MB
Boot services exited
GDT loaded
Turtle OS kernel_main reached!
Kernel initialized.

The first three lines come from UEFI console output (before EBS). The last three come from serial output (after EBS). The QEMU window also shows the framebuffer console output from printk.
