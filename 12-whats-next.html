12. What's Next

At this point, we have a bootable 64-bit kernel that:

  • Boots via UEFI with no external bootloaders
  • Owns the GDT with a TSS (ready for interrupt handling)
  • Writes to both a framebuffer console and a serial port
  • Knows the memory map and framebuffer layout

That's a solid foundation. Here's what comes next, in approximate order of dependency:

1. Page tables

We're currently running on UEFI's identity-mapped page tables. These map virtual address 0–4GB (and possibly more) 1:1 to physical memory. This works for now, but we need our own page tables to:

  • Identity-map low memory (0–1MB) for I/O port access and BIOS/ACPI structures
  • Map the framebuffer at a known virtual address
  • Set up a higher-half kernel (map the kernel to 0xFFFFFFFF80000000 or similar)
  • Eventually implement per-process address spaces

The first step is a simple identity map of the first 4GB using 2MB huge pages (so we only need a P4ML4 + a few PDPT entries + a few PD entries, not thousands of page table entries).

2. IDT and interrupt handling

We disabled interrupts with cli after ExitBootServices. Before we can handle exceptions (page faults, general protection faults, etc.) or hardware interrupts (keyboard, timer, disk), we need to:

  • Set up an Interrupt Descriptor Table (IDT) with 256 entries
  • Write assembly stubs that save registers, call a C handler, and restore registers
  • Remap the PIC (or switch to APIC)
  • Enable interrupts with sti

3. Physical memory allocator

We have the memory map from UEFI, but no way to allocate and free pages. A buddy allocator or a simple bitmap allocator would let us:

  • Allocate pages for page tables
  • Allocate memory for kernel data structures
  • Eventually implement kmalloc and kfree

4. Kernel heap

Once we have a page allocator, we can build a slab or dlmalloc-style heap on top of it. This gives us kmalloc for arbitrary-size allocations.

5. Keyboard input

With the IDT in place, we can handle keyboard interrupts (IRQ1 on the PIC, or the keyboard driver via APIC). This gives us interactive input on the framebuffer console.

6. Timer and scheduling

The Programmable Interval Timer (PIT) or HPET can generate periodic interrupts. Once we have timer interrupts, we can implement cooperative or preemptive multitasking: save the current thread's register state, switch to the next thread, restore its state, and resume.

7. Disk I/O and filesystem

We need to read from disk (virtio-blk in QEMU) and implement at least a simple filesystem (FAT32 is a good start — UEFI already uses it, and the spec is simple). This is a prerequisite for loading user programs.

8. User mode and syscalls

With page tables and the TSS already in place, we can:

  • Create user-mode page tables (ring 3)
  • Use sysret/syscall for fast kernel entry/exit
  • Implement a syscall interface (read, write, open, close, exec, fork, etc.)

9. Porting PCC

The long-term goal is for Turtle OS to be self-hosting: able to compile its own kernel. We've chosen PCC (Portable C Compiler) as the compiler to port because:

  • It supports __attribute__((ms_abi)) (TCC doesn't)
  • It targets C11
  • It's relatively small (~50K lines of code)
  • It's BSD-licensed

PCC currently compiles 5 of our 6 kernel source files (the 6th uses an inline assembly constraint that PCC doesn't support). The next steps for PCC are:

  • Fix the "Nd" constraint issue
  • Make PCC output Turtle OS object files (ELF, with our ABI)
  • Port PCC's runtime support (cpp, assembler linker) to run on Turtle OS

The road ahead

OS development is an iterative process. Each layer builds on the last. The boot chain we've built here — UEFI entry, GOP, memory map, EBS, GDT, kernel_main — is the foundation for everything that follows. Every feature listed above depends on having a working boot and basic console output.

Good luck, and have fun.
