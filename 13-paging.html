13. Page Tables & Identity Mapping

After exiting boot services, our kernel runs on UEFI's page tables. These are an identity map set up by the firmware, and they work — but we don't control them. We need our own page tables to:

  • Know exactly what is mapped and where
  • Map the framebuffer (which may be at a high address like 0x80000000)
  • Later implement higher-half kernel and per-process address spaces
  • Enable NX (No-Execute) bits for security

x86_64 paging overview

In 64-bit long mode, paging uses a 4-level hierarchy: 

Virtual Address (48 bits used)
┌──────────┬──────────┬──────────┬──────────┬──────────────┐
│ PML4 idx │ PDPT idx │  PD idx  │  PT idx  │ Page offset   │
│  9 bits  │  9 bits  │  9 bits  │  9 bits  │   12 bits     │
└──────────┴──────────┴──────────┴──────────┴──────────────┘

Level 4: PML4  (Page Map Level 4) — 512 entries, 8 bytes each = 4KB
Level 3: PDPT  (Page Directory Pointer Table) — 512 entries
Level 2: PD    (Page Directory) — 512 entries
Level 1: PT    (Page Table) — 512 entries

Each entry is 8 bytes. The low 12 bits are flags; the remaining bits are the physical address of the next-level table (or the final page). All tables must be 4KB-aligned.

2MB huge pages

If we use 4KB pages, we need 5 levels of tables to map even 1GB: one PML4, one PDPT, one PD, one PT per 2MB, and the pages themselves. That's a lot of memory just for page tables.

Instead, we use 2MB huge pages. By setting the PS (Page Size) bit (bit 7) in a Page Directory entry, the CPU treats the entry as a 2MB page instead of a pointer to a Page Table. This eliminates one level: 

PML4 → PDPT → PD → 2MB page (no PT needed)

With 2MB pages, a single PD (512 entries × 2MB = 1GB) maps a full gigabyte. To map 4GB, we need just one PML4, one PDPT, and four PD tables: 6 tables × 4KB = 24KB of page tables.

Page table entry flags

BitNameMeaning
0PresentPage is present in memory
1R/WRead/Write (0 = read-only)
2U/SUser/Supervisor (0 = ring 0 only)
5AccessedSet by CPU when page is read
7PS (Huge)Page size: 1 = huge page in PD entry
63NXNo-Execute (prevent code execution)

The page_table struct

struct page_table {
    uint64_t entries[512];
};

The struct itself is just 512 uint64_t entries — no padding can occur, so it needs no packing. Alignment to 4096 bytes is critical (the hardware ignores the low 12 bits of a page-table address, treating them as flags), but it is a per-variable property, not a property of the type. We therefore apply the standard C11 _Alignas specifier at each table's definition: 

static _Alignas(4096) struct page_table pml4;
static _Alignas(4096) struct page_table pdpt[2];
static _Alignas(4096) struct page_table pd[2];

If a table were not 4KB-aligned, the hardware would interpret the misaligned address bits as flags, causing silent corruption. _Alignas is the C11 standard spelling of what GCC spells __attribute__((aligned(4096))); portable to any C11 compiler.

Our mapping strategy

We create two PDPT entries and two PD tables:

  • PML4[0] → PDPT[0] → PD[0] → 512 2MB pages mapping 0–1GB (identity map)
  • PML4[0] PDPT[1] or PDPT[fb_pdpt_idx] → PD[1] → 2MB pages mapping the framebuffer region
  • PML4[256] → same as PML4[0] (higher-half mirror, for future use)

The key challenge: the framebuffer address (0x80000000 = 2GB) falls in PDPT entry 1 (0x80000000 ÷ 512GB = 0, but within PDPT[0], it's PD entry 1: 0x80000000 ÷ 1GB = 2, so PD index = 2). We map it within the first PDPT's PD entry range.

Mapping a 2MB page

static void map_2mb_page(struct page_table *pd, int idx,
                          uint64_t phys, uint64_t flags)
{
    pd->entries[idx] = (phys & 0xFFFFFFFFFFE00000ULL) | flags;
}

The mask 0xFFFFFFFFFFE00000 extracts bits 21–51, which is the physical address aligned to 2MB. The flags (Present, Writable, Huge, etc.) fill the low bits.

Initializing the page tables

void paging_init(uint64_t fb_base, uint64_t fb_size)
{
    memset(&pml4, 0, sizeof(pml4));
    memset(pdpt, 0, sizeof(pdpt));
    memset(pd, 0, sizeof(pd));

    pml4.entries[0] = (uint64_t)&pdpt[0] | PTE_PRESENT | PTE_WRITABLE;
    pml4.entries[256] = pml4.entries[0];  /* higher-half mirror */

    pdpt[0].entries[0] = (uint64_t)&pd[0] | PTE_PRESENT | PTE_WRITABLE;

    /* Identity map 0-1GB using 512 2MB pages */
    for (int i = 0; i < 512; i++) {
        uint64_t phys = (uint64_t)i * HUGEPAGE_SIZE;
        map_2mb_page(&pd[0], i, phys,
                     PTE_PRESENT | PTE_WRITABLE | PTE_HUGE | PTE_ACCESSED);
    }

    /* Map framebuffer region in a second PD */
    if (fb_base != 0 && fb_base < (1ULL << 39)) {
        int fb_pd_idx = pd_index(fb_base);
        if (fb_pd_idx > 0) {
            pdpt[0].entries[fb_pd_idx] =
                (uint64_t)&pd[1] | PTE_PRESENT | PTE_WRITABLE;
            for (int i = 0; i < 512; i++) {
                uint64_t phys = (uint64_t)fb_pd_idx * (1ULL << 30)
                              + (uint64_t)i * HUGEPAGE_SIZE;
                map_2mb_page(&pd[1], i, phys,
                             PTE_PRESENT | PTE_WRITABLE | PTE_HUGE
                             | PTE_ACCESSED | PTE_NX);
            }
        }
    }
}

We mark the framebuffer pages with PTE_NX (No-Execute) because the framebuffer is data, not code. This is a security best practice: if an attacker can write to the framebuffer, they shouldn't be able to execute what they wrote.

Loading the page tables

paging_load() configures the CPU to use our page tables. We must set several control registers and an MSR: 

void paging_load(void)
{
    uint64_t cr4, efer;

    /* Enable PAE (Physical Address Extension) and PSE (Page Size Extension) */
    cr4 = read_cr4();
    cr4 |= CR4_PAE | CR4_PSE;
    write_cr4(cr4);

    /* Set EFER.LME (Long Mode Enable) and EFER.NXE (No-Execute Enable) */
    efer = read_msr(0xC0000080);
    efer |= EFER_LME | EFER_NXE;
    write_msr(0xC0000080, efer);

    /* Load our PML4 address into CR3 */
    write_cr3((uint64_t)&pml4);

    /* Enable paging (CR0.PG = bit 31) and write-protect (CR0.WP = bit 16) */
    uint64_t cr0;
    cr0 = read_cr0();
    cr0 |= CR0_WP;
    cr0 |= (uint64_t)1 << 31;
    write_cr0(cr0);
}

Each control-register and MSR access goes through a C-callable wrapper in src/arch/x86_64/intrinsics.S — read_cr0/write_cr0, read_cr3/write_cr3, read_cr4/write_cr4, and read_msr/write_msr. Keeping the mov %%cr4, %0 and rdmsr/wrmsr sequences in assembly keeps the C source portable ANSI C11: the compiler only sees ordinary function calls, never inline-asm. read_msr combines the high 32 bits from rdx with the low 32 bits from rax into a single 64-bit return value; write_msr performs the opposite split.

Important: we're already in 64-bit long mode (UEFI set that up), so the CPU is already using some page tables. We're just replacing them with our own. The CR0.PG bit is already set; writing it again is harmless. The key steps are: set CR3 (our PML4 address), enable PAE/PSE features, and set NX in EFER.

If we were transitioning from 32-bit protected mode to long mode, the order would matter: set CR4.PAE first, then EFER.LME, then CR3, then CR0.PG. Since UEFI already did this, our paging_load just swaps the page tables and adds features (NX).

The higher-half mirror

pml4.entries[256] = pml4.entries[0];

PML4 entry 256 covers virtual addresses 0xFFFF800000000000–0xFFFF80FFFFFFFFF (the "negative" address space in canonical form). By mirroring entry 0 here, we create a higher-half alias of the same memory. When we later move the kernel to a higher-half address, this mapping will be the primary one.

What this gives us

  • Identity-mapped first 1GB — all code, data, stack, and low-memory hardware structures are accessible
  • Framebuffer mapped — the GOP framebuffer (at 0x80000000 or wherever) is writable, with NX set
  • NX bit enabled — the framebuffer and future data-only mappings are non-executable
  • Higher-half ready — PML4[256] mirrors the low mapping, ready for kernel relocation
  • Full control — we know every mapping; no surprises from UEFI's page tables
