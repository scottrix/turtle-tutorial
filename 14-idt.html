14. The IDT & Exception Handling

With page tables active, the next critical piece is the Interrupt Descriptor Table (IDT). Without it, any CPU exception (page fault, general protection fault, divide error) causes a triple fault — the CPU resets with no diagnostic output. With an IDT, we can catch exceptions, dump register state, and either recover or halt cleanly.

What is the IDT?

The IDT is an array of 256 descriptors, each 16 bytes in 64-bit mode. The CPU uses the interrupt vector number (0–255) as an index into the IDT to find the handler address. There are three types:

  • Interrupt gates (type 0xE) — disable interrupts on entry (IF is cleared)
  • Trap gates (type 0xF) — leave interrupts enabled (used for breakpoints, int 3)
  • Task gates — hardware task switch (not used in 64-bit mode)

IDT entry layout (64-bit)

Bytes 0-1:  Offset[15:0]  (low 16 bits of handler address)
Byte 2:    Segment Selector (our code segment: 0x08)
Byte 3:    IST (Interrupt Stack Table offset, 0 = none)
Byte 4:    Type Attributes (Present, DPL, Gate Type)
Bytes 5-6: Offset[31:16] (mid 16 bits)
Bytes 7-10: Offset[63:32] (high 32 bits)
Bytes 11-15: Reserved (must be zero)

The handler address is split across three fields (low, mid, high). The segment selector tells the CPU which code segment the handler runs in — we use our kernel code selector 0x08.

The type_attr byte

Byte 4 of each IDT entry is the type/attributes byte, with this bit layout: 

Bit 7:    Present (1 = handler is valid)
Bits 6-5: DPL (Descriptor Privilege Level, 0 = kernel only)
Bits 4-0: Gate type (0x0E = interrupt, 0x0F = trap)

Common values:

ConstantValueMeaning
IDT_PRESENT | IDT_INTERRUPT | IDT_DPL00x8EKernel interrupt gate
IDT_PRESENT | IDT_TRAP | IDT_DPL30xEFUser-accessible trap gate (for int 3)

CPU exceptions: vectors 0–31

The Intel architecture reserves vectors 0–31 for CPU exceptions:

Some exceptions push an error code onto the stack; others don't. Our assembly stubs handle this by pushing a fake 0 for exceptions that don't push one, so the stack frame is uniform.

The assembly stubs

Each ISR (Interrupt Service Routine) is a tiny assembly stub that:

  1. Pushes a dummy error code (0) if the CPU doesn't push one
  2. Pushes the vector number
  3. Jumps to the common handler
.macro ISR_NOERR n
.global isr\n
isr\n:
push $0          /* fake error code */
push $\n         /* vector number */
jmp isr_common
.endm

.macro ISR_ERR n
.global isr\n
isr\n:
push $\n         /* CPU already pushed error code */
jmp isr_common
.endm

Exceptions that push error codes (8, 10–14, 17, 21, 29, 30) use ISR_ERR; all others use ISR_NOERR.

The common handler

The common handler saves all general-purpose registers, calls the C function, then restores everything and returns: 

isr_common:
push %r15
push %r14
...
push %rax          /* save all 15 GP registers */

mov %rsp, %rdi     /* first arg = pointer to frame */
call exception_handler  /* C handler */

pop %rax
...
pop %r15           /* restore registers */
add $16, %rsp      /* remove error code + vector number */
iretq              /* return from interrupt */

iretq pops RIP, CS, RFLAGS, RSP, and SS from the stack (the CPU pushed these before entering the handler). This restores the exact pre-interrupt state.

The interrupt frame struct — field order matters!

The struct fields must match the push order in the assembly stub. Since push %rax is the last push, rax is at the lowest address (offset 0) on the stack. C structs lay out fields in declaration order from low to high address, so rax must be first: 

struct interrupt_frame {
uint64_t rax, rbx, rcx, rdx, rbp, rsi, rdi;
uint64_t r8, r9, r10, r11, r12, r13, r14, r15;
uint64_t int_no, error_code;
uint64_t rip, cs, rflags, rsp, ss;
};

Warning: If you reverse the struct order (r15 first, rax last), the handler will read garbage values for all registers. This is one of the most common IDT bugs — the push order and the struct declaration order must be opposites (last pushed = first in the struct).

Writing IDT entries in pure assembly

Under UEFI, our kernel is compiled with -fpic (position- independent code). This creates a subtle trap: if we store handler function pointers in a local array, the compiler copies them from the .data section via rep movsq — but the .data source has unrelocated ELF virtual addresses. The properly relocated addresses live in the GOT (Global Offset Table), which the UEFI PE loader fixes up. When the compiler reads from the local array copy, it gets the wrong values.

The fix: don't use a local array. Instead, pass each handler directly to a function that reads it via the GOT: 

static void idt_set_entry(int idx, void *handler, uint8_t type_attr)
{
volatile void *entry = (volatile void *)(IDT_PHYS_ADDR + idx * 16);
volatile uint64_t h = (uint64_t)(uintptr_t)handler;
idt_set_entry_asm((void *)entry, h, type_attr);
}

/* Each call forces a GOT-relative read of the handler address */
idt_set_entry(0, isr0, IDT_PRESENT | IDT_INTERRUPT | IDT_DPL0);
idt_set_entry(1, isr1, IDT_PRESENT | IDT_INTERRUPT | IDT_DPL0);
/* ... */

The volatile uint64_t h forces the compiler to do a full 64-bit GOT read for each handler address. The idt_set_entry_asm function is written in pure assembly to reliably split the 64-bit handler address into the IDT entry's offset_low, offset_mid, and offset_high fields: 

idt_set_entry_asm:
/* rdi = entry address, rsi = handler, dl = type_attr */
mov %rsi, %rax
mov %rsi, %rcx
shr $16, %rax
shr $32, %rcx
movb %sil, (%rdi)       /* offset[7:0] */
shr $8, %rsi
movb %sil, 1(%rdi)      /* offset[15:8] */
movw $0x0008, 2(%rdi)   /* segment selector */
movb $0x00, 4(%rdi)     /* IST */
movb %dl, 5(%rdi)       /* type_attr */
movb %al, 6(%rdi)       /* offset[23:16] */
shr $8, %rax
movb %al, 7(%rdi)       /* offset[31:24] */
movb %cl, 8(%rdi)       /* offset[39:32] */
shr $8, %rcx
movb %cl, 9(%rdi)       /* offset[47:40] */
shr $8, %rcx
movb %cl, 10(%rdi)      /* offset[55:48] */
shr $8, %rcx
movb %cl, 11(%rdi)      /* offset[63:56] */
movq $0, 12(%rdi)       /* reserved */
ret

Setting TSS RSP0

When an interrupt fires while running in ring 3, the CPU switches to the stack pointer in TSS.RSP0 before calling the IDT handler. We must set this to a valid kernel stack: 

static _Alignas(16) uint8_t kernel_stack[16384];
struct tss_entry *tss = gdt_get_tss();
uint64_t kstack_top = (uint64_t)&kernel_stack[sizeof(kernel_stack)];
tss->rsp[0] = kstack_top;
set_rsp(kstack_top);

We point RSP0 to the top of the stack array because x86 stacks grow downward. We also switch RSP to this kernel stack, since after ExitBootServices and the GDT reload, we need a known-good stack for interrupt handling. The 16-byte alignment uses the standard C11 _Alignas specifier rather than the GCC-specific __attribute__((aligned(16))), and the RSP switch goes through the set_rsp wrapper in intrinsics.S rather than inline assembly.

Loading the IDT

idt_init();                    /* fill all 256 entries */
idt_load();                    /* lidt instruction */
cpu_sti();                     /* enable interrupts */

lidt loads the IDT pointer (limit + base address), just like lgdt does for the GDT. After this, the CPU uses our IDT for all exceptions and interrupts.
