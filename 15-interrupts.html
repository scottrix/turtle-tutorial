15. Hardware Interrupts — PIC, PIT, and Keyboard

With the IDT loaded and exceptions handled, we can now enable hardware interrupts. This chapter covers the three pieces that make this work: remapping the PIC (Programmable Interrupt Controller) so IRQs don't collide with CPU exceptions, programming the PIT (Programmable Interval Timer) to generate periodic ticks, and writing a keyboard driver that reads scancodes from the PS/2 controller.

The 8259 PIC

The 8259 PIC is the legacy interrupt controller on x86. In a PC, two PIC chips are cascaded: a master (IRQs 0–7) and a slave (IRQs 8–15, cascaded on the master's IRQ 2). By default, the BIOS maps IRQs 0–15 to INT 8–15, which collides with CPU exceptions (double fault, GPF, page fault). We must remap the PIC to use vectors 32–47, which are safely above the reserved exception vectors.

PIC I/O ports

PortFunction
0x20Master PIC Command
0x21Master PIC Data (mask)
0xA0Slave PIC Command
0xA1Slave PIC Data (mask)

PIC initialization sequence

The PIC is initialized with four ICW (Initialization Command Words), written sequentially to the command port. Between writes, we do an I/O wait (writing to port 0x80) to give the slow PIC time to process: 

void pic_init(void)
{
/* Mask all IRQs first */
outb(0xFF, PIC_MASTER_DATA);
outb(0xFF, PIC_SLAVE_DATA);

/* ICW1: Start initialization in cascade mode */
outb(ICW1_INIT | ICW1_ICW4, PIC_MASTER_CMD);
io_wait();
outb(ICW1_INIT | ICW1_ICW4, PIC_SLAVE_CMD);
io_wait();

/* ICW2: Vector offsets - master at 0x20, slave at 0x28 */
outb(0x20, PIC_MASTER_DATA);
io_wait();
outb(0x28, PIC_SLAVE_DATA);
io_wait();

/* ICW3: Cascade wiring - master has slave on IRQ2,
          slave has cascade identity 2 */
outb(0x04, PIC_MASTER_DATA);
io_wait();
outb(0x02, PIC_SLAVE_DATA);
io_wait();

/* ICW4: 8086 mode */
outb(ICW4_8086, PIC_MASTER_DATA);
io_wait();
outb(ICW4_8086, PIC_SLAVE_DATA);
io_wait();

/* Mask all IRQs again (will unmask selectively later) */
outb(0xFF, PIC_MASTER_DATA);
outb(0xFF, PIC_SLAVE_DATA);
}

After this, IRQ 0 fires as INT 0x20, IRQ 1 as INT 0x21, and so on up to IRQ 15 at INT 0x2F. These map to our IDT entries 32–47.

EOI (End of Interrupt)

After handling an IRQ, you must send an EOI to the PIC, or it will never deliver another interrupt. For IRQs 8–15 (which come through the slave), you must send EOI to both PICs: 

void pic_eoi(uint8_t irq)
{
if (irq >= 8)
outb(0x20, PIC_SLAVE_CMD);   /* slave first */
outb(0x20, PIC_MASTER_CMD);   /* then master */
}

Masking and unmasking IRQs

Each PIC has an 8-bit interrupt mask register. A set bit means the corresponding IRQ is masked (disabled). We unmask only the IRQs we need: 

void pic_unmask(uint8_t irq)
{
uint16_t port;
if (irq < 8)
port = PIC_MASTER_DATA;
else {
port = PIC_SLAVE_DATA;
irq -= 8;
}
uint8_t value = inb(port) & ~(1 << irq);
outb(value, port);
}

The PIT (Programmable Interval Timer)

The 8254 PIT is a simple timer that generates interrupts on IRQ 0 at a configurable frequency. The base clock is approximately 1.193182 MHz (1193182 Hz). We set a 16-bit divisor; the output frequency is 1193182 / divisor.

PIT I/O ports

PortFunction
0x40Channel 0 data (the one that generates IRQ 0)
0x43Command register

Initializing the PIT

#define PIT_FREQ 1193182

void pit_init(uint32_t freq)
{
uint16_t divisor = (uint16_t)(PIT_FREQ / freq);

outb(0x36, PIT_COMMAND);           /* channel 0, lobyte/hibyte, mode 3 */
outb((uint8_t)(divisor & 0xFF), PIT_CHANNEL0);    /* low byte */
outb((uint8_t)((divisor >> 8) & 0xFF), PIT_CHANNEL0); /* high byte */
}

Mode 3 is "square wave generator" — it toggles the output, which is what we want for a periodic timer. With freq = 100, the divisor is 11931 and we get 100 ticks per second.

The tick counter

static volatile uint64_t pit_ticks = 0;

void pit_handler(void)
{
pit_ticks++;
}

uint64_t pit_get_ticks(void)
{
return pit_ticks;
}

The handler is called from our exception_handler when int_no == 32 (IRQ 0). The volatile qualifier ensures the compiler re-reads the variable each time, even in a loop.

The PS/2 Keyboard

The PS/2 keyboard controller sends scancodes on IRQ 1 (INT 0x21). When a key is pressed, the controller sends a "make" scancode; when released, it sends a "break" scancode (make code with bit 7 set). We read the scancode from port 0x60: 

#define KEYBOARD_DATA 0x60

void keyboard_handler(void)
{
uint8_t scancode = inb(KEYBOARD_DATA);

/* Ignore break codes (bit 7 set) */
if (scancode & 0x80)
return;

/* Convert to ASCII if we have a mapping */
if (scancode < 128) {
char c = scancode_to_ascii[scancode];
if (c) {
kb_buffer[kb_write_pos & 0xFF] = c;
kb_write_pos++;
}
}
}

Scancode to ASCII table

The PS/2 keyboard sends "set 1" scancodes by default. Here is the lookup table for US keyboard layout (make codes only): 

static const char scancode_to_ascii[128] = {
0, 27, '1', '2', '3', '4', '5', '6', '7', '8', '9', '0', '-', '=', '\b',
'\t', 'q', 'w', 'e', 'r', 't', 'y', 'u', 'i', 'o', 'p', '[', ']', '\n',
0, 'a', 's', 'd', 'f', 'g', 'h', 'j', 'k', 'l', ';', '\'', '`',
0, '\\', 'z', 'x', 'c', 'v', 'b', 'n', 'm', ',', '.', '/', 0,
'*', 0, ' '
};

The ring buffer

The keyboard handler runs in interrupt context and must return quickly. We store incoming characters in a circular ring buffer and let the kernel's main loop consume them at its leisure: 

static volatile char kb_buffer[256];
static volatile uint32_t kb_write_pos = 0;
static volatile uint32_t kb_read_pos = 0;

char keyboard_get_char(void)
{
if (kb_read_pos == kb_write_pos)
return 0;
char c = kb_buffer[kb_read_pos & 0xFF];
kb_read_pos++;
return c;
}

int keyboard_has_char(void)
{
return kb_read_pos != kb_write_pos;
}

The 256-byte buffer wraps naturally via the & 0xFF mask. The 32-bit positions never wrap to each other accidentally, so the "empty" check (read == write) works correctly.

Wiring it all together

In efi_main.c, after loading the IDT, we initialize the PIC, PIT, and keyboard, then unmask the IRQs we want: 

idt_init();
idt_load();

pic_init();           /* remap IRQs to INT 32-47 */
pit_init(100);        /* 100 Hz timer */
keyboard_init();

pic_unmask(0);        /* enable IRQ 0 (timer) */
pic_unmask(1);        /* enable IRQ 1 (keyboard) */

cpu_sti();                 /* enable CPU interrupts */

Our exception_handler now dispatches hardware IRQs to their respective handlers and sends EOI: 

void exception_handler(struct interrupt_frame *frame)
{
if (frame->int_no >= 32 && frame->int_no < 48) {
irq_handler((uint8_t)(frame->int_no - 32));
pic_eoi((uint8_t)(frame->int_no - 32));
} else if (frame->int_no < 32) {
/* CPU exception - halt */
cpu_cli();
for (;;)
cpu_halt();
}
}

static void irq_handler(uint8_t irq)
{
switch (irq) {
case 0: pit_handler(); break;
case 1: keyboard_handler(); break;
}
}

The kernel main loop

With interrupts enabled, the kernel main loop can now respond to timer ticks and keyboard input: 

uint64_t last_ticks = 0;
for (;;) {
uint64_t ticks = pit_get_ticks();
if (ticks != last_ticks && (ticks % 100 == 0)) {
serial_puts("Tick: ");
serial_put_dec(ticks);
serial_puts("\n");
last_ticks = ticks;
}
if (keyboard_has_char()) {
char c = keyboard_get_char();
serial_out(c);
}
cpu_halt();                 /* sleep until next interrupt */
}

The hlt instruction halts the CPU until the next interrupt arrives, saving power. Each timer tick wakes the CPU, and we check if a full second has elapsed (every 100 ticks). Keyboard input is echoed to the serial port as it arrives.

Running it

Build and run the OS. You should see the timer counting seconds on the serial output: 

$ make efi-run
Boot services exited
Turtle OS kernel_main reached!
Kernel initialized.
Tick: 100
Tick: 200
Tick: 300
...

If you type in the QEMU window, characters are echoed to the serial port. The OS is now responding to the outside world — it's alive!

A note on the -fpic GOT trap

This chapter's code works because we learned a painful lesson in Chapter 14: with -fpic, storing function pointers in a local array copies unrelocated values from .data. Each handler must be read individually via the GOT to get the correct runtime address. The same principle applies to any global function pointer in a PIC binary — if you need the runtime address, read it through the GOT, not from a copied array.
