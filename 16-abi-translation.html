16. The ABI Translation Layer

In earlier chapters, we used __attribute__((ms_abi)) to let GCC handle the ABI difference between our C code (System V AMD64) and UEFI firmware functions (Microsoft x64). This worked, but it created a dependency on a GCC-specific extension. If we want our OS to be compilable with other compilers — specifically PCC (Portable C Compiler), which does not support __attribute__((ms_abi)) — we need a different approach.

This chapter presents the solution: a pure-assembly ABI translation layer that sits between our C code and UEFI. No C function in the entire codebase needs EFIAPI or __attribute__((ms_abi)). The compiler doesn't need to know about the Microsoft calling convention at all.

The Problem

UEFI firmware functions expect to be called with the Microsoft x64 ABI:

Arg #MS ABI RegisterSysV ABI Register
1strcxrdi
2ndrdxrsi
3rdr8rdx
4thr9rcx
5th+stackstack

Additionally, the MS ABI requires 32 bytes of shadow space on the stack (for the callee to optionally spill the four register arguments), and the stack must be 16-byte aligned at the point of the call instruction.

With __attribute__((ms_abi)), GCC generates all the register shuffling and shadow space allocation automatically. But this is a GCC extension. PCC doesn't support it. If we want to self-host with PCC someday, we need an alternative.

The Solution: Assembly Wrappers

Instead of annotating C functions with EFIAPI, we write assembly wrappers that:

  1. Receive arguments in the System V ABI convention (rdi, rsi, rdx, rcx, r8, r9, stack)
  2. Shuffle the registers into the Microsoft x64 convention (rcx, rdx, r8, r9)
  3. Allocate shadow space and align the stack
  4. Move stack arguments to their correct MS ABI positions
  5. Call the UEFI function pointer
  6. Return the result (rax is the same in both ABIs)

We provide one wrapper per argument count: efi_call0 through efi_call6. The C header declares them like this: 

#ifndef TURTLE_EFI_CALL_H
#define TURTLE_EFI_CALL_H

#include <kernel/types.h>

uint64_t efi_call0(void *func);
uint64_t efi_call1(void *func, void *a1);
uint64_t efi_call2(void *func, void *a1, void *a2);
uint64_t efi_call3(void *func, void *a1, void *a2, void *a3);
uint64_t efi_call4(void *func, void *a1, void *a2, void *a3, void *a4);
uint64_t efi_call5(void *func, void *a1, void *a2, void *a3, void *a4, void *a5);
uint64_t efi_call6(void *func, void *a1, void *a2, void *a3, void *a4, void *a5, void *a6);

#endif

All arguments are void *. This is deliberate: the assembly code treats every argument as a 64-bit value and passes it in a register or on the stack. The C caller casts as needed.

Register Mapping

The core of every wrapper is the register shuffle. Our C code calls efi_callN(func, a1, a2, ...). In the System V ABI, the arguments arrive as:

ArgumentSysV RegisterMS ABI Target
funcrdiused by call *%rdi
a1rsircx
a2rdxrdx (already there!)
a3rcxr8
a4r8r9
a5r9stack [rsp+0x20]
a6stack [rsp+0x08]stack [rsp+0x28]
Note that a2 is already in the right register (rdx). The SysV ABI and MS ABI both use rdx for the 2nd argument. This saves us one move in every wrapper.

The register shuffle must be done in the right order to avoid clobbering. For efi_call3, we need a3 (in rcx) to go to r8, and a1 (in rsi) to go to rcx. If we move rsi to rcx first, we lose a3. So we move a3 first: 

mov %rcx, %r8    /* a3 → R8 (must happen before rcx is overwritten) */
mov %rsi, %rcx   /* a1 → RCX */

For efi_call4, the chain is longer: a4 (r8) → r9, a3 (rcx) → r8, a1 (rsi) → rcx. Again, we must move from the end of the chain first: 

mov %r8, %r9    /* a4 → R9 (r8 is source, r9 is destination) */
mov %rcx, %r8   /* a3 → R8 (rcx still has original a3) */
mov %rsi, %rcx  /* a1 → RCX */
The MS ABI register order is RCX, RDX, R8, R9 — not RCX, RDX, R9, R8. Using the wrong order would cause efi_call3 to put the 3rd argument into R9 (the 4th-argument slot) instead of R8 (the 3rd-argument slot); the callee would then read its 3rd argument from the wrong register.

Shadow Space and Stack Alignment

The Microsoft x64 ABI has two stack requirements:

  1. Shadow space: The caller must reserve 32 bytes (4 × 8) on the stack before the call, even if the function takes fewer than 4 arguments. This space is at [rsp+0x08] through [rsp+0x27] from the callee's perspective (after the return address is pushed).
  2. 16-byte alignment: The stack must be 16-byte aligned at the point of the call instruction (i.e., the value of rsp just before call must be a multiple of 16).

When our wrapper is entered, the stack looks like this: 

[rsp]        = return address (pushed by the caller's call instruction)
[rsp+0x08]   = a6 (for efi_call6)
[rsp+0x10]   = caller's stuff
...

Since the caller's rsp was 16-byte aligned before calling us, and call pushes 8 bytes, our entry rsp is 16n+8 (8 mod 16). To get back to 16-byte alignment before our own call, we need to subtract an amount that makes rsp congruent to 16n+8 minus our_subtraction equal to 16m+8 (so that after call pushes 8 bytes, rsp = 16m).

For wrappers with no stack arguments (efi_call0 through efi_call4): 

/* entry rsp = 16n+8 */
sub $0x28, %rsp   /* rsp = 16n+8-40 = 16m+8; 40 mod 16 = 8 */
call *%rdi        /* pushes ret addr: rsp = 16m ✓ aligned */

Wait — for efi_call4, we only need 32 bytes (0x20) of shadow space, not 40 (0x28). With 0 args on the stack, we subtract 0x28 to get both shadow space and alignment. With efi_call4 (still no stack args), we subtract 0x20. Let's verify: 

/* entry rsp = 16n+8 */
sub $0x20, %rsp   /* rsp = 16n+8-32 = 16m+8; 32 mod 16 = 0, so 16n+8-32 = 16(n-2)+8 */
call *%rdi        /* pushes ret addr: rsp = 16m ✓ aligned */

That works too. The extra 8 bytes in efi_call0-3's sub $0x28 doesn't hurt — it just wastes 8 bytes of stack. We use $0x28 for efi_call0-3 and $0x20 for efi_call4 for consistency.

efi_call0 through efi_call3

For 0 to 3 arguments, all arguments fit in registers. We just need shadow space and the register shuffle: 

.global efi_call0
efi_call0:
	sub $0x28, %rsp
	call *%rdi
	add $0x28, %rsp
	ret

.global efi_call1
efi_call1:
	sub $0x28, %rsp
	mov %rsi, %rcx        /* a1 → RCX */
	call *%rdi
	add $0x28, %rsp
	ret

.global efi_call2
efi_call2:
	sub $0x28, %rsp
	mov %rsi, %rcx        /* a1 → RCX, a2 already in RDX */
	call *%rdi
	add $0x28, %rsp
	ret

.global efi_call3
efi_call3:
	sub $0x28, %rsp
	mov %rcx, %r8         /* a3 → R8 (move before rcx is clobbered) */
	mov %rsi, %rcx        /* a1 → RCX */
	call *%rdi
	add $0x28, %rsp
	ret

Note how efi_call2 doesn't touch rdx at all — the 2nd argument is already in the correct register.

efi_call4: Four Register Arguments

With four arguments, all still fit in registers. We need the full register chain shuffle: 

.global efi_call4
efi_call4:
	sub $0x20, %rsp
	mov %r8, %r9          /* a4 → R9 */
	mov %rcx, %r8         /* a3 → R8 */
	mov %rsi, %rcx        /* a1 → RCX */
	call *%rdi
	add $0x20, %rsp
	ret

Example: efi_call4(g_BS->SetWatchdogTimer, 0, 0, 0, NULL) puts 0 in rcx, 0 in rdx, 0 in r8, and NULL in r9. The UEFI function receives exactly what it expects.

efi_call5: Five Arguments with Stack

With five arguments, the 5th argument goes on the stack. This is where things get tricky. The MS ABI expects the 5th argument at [rsp+0x28] from the callee's perspective (after the return address is pushed by call), which is [rsp+0x20] from the caller's perspective (before call).

We use a frame pointer approach: push rbp, save rsp into rbp, push the 5th argument, then allocate shadow space: 

.global efi_call5
efi_call5:
	push %rbp
	mov %rsp, %rbp
	push %r9              /* a5: push 5th arg onto stack */
	sub $0x20, %rsp       /* shadow space (32 bytes) */
	mov %r8, %r9          /* a4 → R9 */
	mov %rcx, %r8         /* a3 → R8 */
	mov %rsi, %rcx        /* a1 → RCX */
	call *%rdi
	leave                 /* restore rsp from rbp, pop rbp */
	ret

Let's trace the stack layout. After push %rbp; mov %rsp,%rbp; push %r9; sub $0x20,%rsp, and then call *%rdi: 

/* Before call, rsp = entry_rsp - 8(rbp) - 8(a5) - 0x20(shadow) = entry_rsp - 0x30 */
/* After call pushes ret addr, callee rsp = entry_rsp - 0x38 */

/* Callee sees:                                              */
/*   [rsp+0x00] = return address                             */
/*   [rsp+0x08..0x27] = shadow space (32 bytes)              */
/*   [rsp+0x28] = 5th argument                               */

/* The push of a5 landed at [entry_rsp - 0x10] = [rbp - 8]  */
/* = [callee rsp + 0x28]  ✓  */

The 5th argument is exactly where the callee expects it. And the stack is 16-byte aligned: entry rsp was 16n+8, we subtracted 0x30 (48 bytes), so pre-call rsp = 16n+8-48 = 16(n-3)+8. After call pushes 8 bytes: rsp = 16(n-3). Aligned.

We use leave for cleanup, which is equivalent to mov %rbp, %rsp; pop %rbp. This restores the stack regardless of how much shadow space or how many pushes we did.

efi_call6: Six Arguments with Stack

With six arguments, both the 5th and 6th go on the stack. We can't simply push both, because the alignment and position must be exact. Instead, we allocate all the space at once with sub and mov the stack arguments into place: 

.global efi_call6
efi_call6:
	push %rbp
	mov %rsp, %rbp
	sub $0x38, %rsp       /* 0x20 shadow + 0x10 for two stack args + 0x08 alignment */
	mov %r8, %r9          /* a4 → R9 */
	mov %rcx, %r8         /* a3 → R8 */
	mov %rsi, %rcx        /* a1 → RCX */
	mov 0x10(%rbp), %rax  /* a6: read from caller's stack (via frame pointer) */
	mov %rax, 0x20(%rsp)  /* a6 → [RSP+0x20] (5th arg position from caller) */
	mov %r9, 0x28(%rsp)   /* a5 → [RSP+0x28] (6th arg position from caller) */
	call *%rdi
	leave
	ret

Where is the 6th argument?

The 6th argument arrives on the stack from our C caller. When efi_call6 is entered, the stack looks like: 

[rsp+0x00] = return address (from caller's call to efi_call6)
[rsp+0x08] = a6 (7th value on the stack: func, a1..a5 in regs, a6 on stack)

After push %rbp, rsp decreases by 8. So the old rsp was rbp + 8. The 6th argument was at [old rsp + 0x08] = [rbp + 0x10]. That's why we read it with mov 0x10(%rbp), %rax.

Stack argument positions

After sub $0x38, %rsp, the stack before call looks like: 

[rsp+0x00..0x1F] = shadow space (32 bytes)
[rsp+0x20]       = 5th argument (from callee perspective: [callee_rsp+0x28])
[rsp+0x28]       = 6th argument (from callee perspective: [callee_rsp+0x30])

After call *%rdi pushes the return address, the callee sees its 5th argument at [rsp+0x28] and 6th at [rsp+0x30] — exactly as the MS ABI specifies.

Alignment

Entry rsp = 16n+8. After push rbp (8 bytes) and sub $0x38 (56 bytes): rsp = 16n+8-8-56 = 16n-56 = 16(n-4)+8-8 = 16(n-4). Wait — 16n+8-64 = 16(n-4)+8. After call pushes 8: 16(n-4). Aligned.

The Entry Point: _efi_entry

The same ABI translation is needed at the entry point. UEFI firmware calls our PE entry point with the MS ABI (ImageHandle in rcx, SystemTable in rdx). We need to translate this to the SysV ABI before calling our C efi_main: 

.global _efi_entry
_efi_entry:
	mov %rcx, %rdi        /* ImageHandle: RCX → RDI */
	mov %rdx, %rsi        /* SystemTable: RDX → RSI */
	sub $0x28, %rsp       /* shadow space for efi_main */
	call efi_main
	add $0x28, %rsp
	ret

This is the inverse of the efi_call wrappers: UEFI calls us with MS ABI, and we translate to SysV ABI for our C code. The linker script sets ENTRY(_efi_entry) so the PE header points here.

Changes to efi.h

With the ABI translation layer, we no longer need __attribute__((ms_abi)) anywhere in C code. The efi.h header changes dramatically:

Before (with EFIAPI)

#define EFIAPI __attribute__((ms_abi))

typedef EFI_STATUS EFIAPI efi_get_memory_map(UINTN *MemoryMapSize,
    void *MemoryMap, UINTN *MapKey, UINTN *DescriptorSize,
    UINT32 *DescriptorVersion);

typedef struct {
    EFI_TABLE_HEADER Hdr;
    void *RaiseTPL;
    void *RestoreTPL;
    efi_allocate_pages *AllocatePages;
    efi_free_pages *FreePages;
    efi_get_memory_map *GetMemoryMap;
    efi_allocate_pool *AllocatePool;
    /* ... */
} EFI_BOOT_SERVICES;

After (with assembly wrappers)

/* No EFIAPI macro! */

typedef struct {
    EFI_TABLE_HEADER Hdr;
    void *RaiseTPL;
    void *RestoreTPL;
    void *AllocatePages;
    void *FreePages;
    void *GetMemoryMap;
    void *AllocatePool;
    /* ... */
} EFI_BOOT_SERVICES;

Every function pointer in every EFI struct becomes void *. We don't need typed function pointers because we never call them directly — we always pass them through the assembly wrappers.

Changes to efi_main.c

In efi_main.c, every UEFI call changes from a direct function pointer call to an efi_callN() wrapper:

Before

g_ST->ConOut->ClearScreen(g_ST->ConOut);
g_ST->ConOut->OutputString(g_ST->ConOut, buf);
g_BS->SetWatchdogTimer(0, 0, 0, NULL);
g_BS->LocateHandle(2, &gop_guid, NULL, &buf_sz, handles);
g_BS->GetMemoryMap(&map_size, memory_map, &map_key, &desc_size, &desc_ver);
g_BS->AllocatePool(EfiLoaderData, map_size, (void **)&memory_map);
g_BS->ExitBootServices(ImageHandle, ebs_map_key);

After

efi_call1(g_ST->ConOut->ClearScreen, g_ST->ConOut);
efi_call2(g_ST->ConOut->OutputString, g_ST->ConOut, buf);
efi_call4(g_BS->SetWatchdogTimer, (void *)0, (void *)0, (void *)0, NULL);
efi_call5(g_BS->LocateHandle, (void *)2, &gop_guid, NULL, &buf_sz, handles);
efi_call5(g_BS->GetMemoryMap, &map_size, memory_map, &map_key, &desc_size, &desc_ver);
efi_call3(g_BS->AllocatePool, (void *)EfiLoaderData, (void *)map_size, (void **)&memory_map);
efi_call2(g_BS->ExitBootServices, ImageHandle, (void *)ebs_map_key);

Note that integer arguments must be cast to void * since the wrapper declarations use void * for all parameters. This is a minor inconvenience but ensures type-agnosticism in the assembly layer.

Also, efi_main itself no longer needs EFIAPI: 

/* Before: */
EFI_STATUS EFIAPI efi_main(EFI_HANDLE ImageHandle, EFI_SYSTEM_TABLE *SystemTable)

/* After: */
uint64_t efi_main(EFI_HANDLE ImageHandle, EFI_SYSTEM_TABLE *SystemTable)

The return type changes to uint64_t (a plain C type) since the SysV ABI caller (_efi_entry) will receive the return value in rax, which is the same register in both conventions.

Bugs We Hit

Building this layer was one of the hardest debugging sessions in the entire project. Here are the specific bugs we encountered:

Bug 1: R8/R9 swap in efi_call2 and efi_call3

Our initial efi_call2 put the 2nd argument into R8 (the MS ABI's 3rd arg register) instead of leaving it in RDX (where it already was). And efi_call3 put the 3rd argument into R9 instead of R8. We had the MS ABI register order wrong: RCX, RDX, R9, R8 instead of the correct RCX, RDX, R8, R9.

Symptom: AllocatePool returned EFI_SUCCESS but wrote the allocated pointer to the wrong output parameter (because the 3rd arg was in R9 instead of R8). Our memory_map pointer stayed NULL, causing GetMemoryMap to fail with EFI_INVALID_PARAMETER.

Bug 2: Wrong shadow space size in efi_call5

We initially used sub $0x20 without the frame pointer push, which put the stack-arg push at the wrong offset relative to where the callee expected it. The 5th argument needs to be at [callee_rsp + 0x28], but without accounting for the return address push, it ended up 8 bytes off.

Bug 3: Wrong stack-arg offsets in efi_call6

We initially wrote the 5th and 6th arguments to 0x28(%rsp) and 0x30(%rsp) (the callee's perspective offsets), but these offsets are from the callee's rsp, which is 8 bytes different from the caller's rsp (due to the return address push). The correct offsets from the caller's pre-call rsp are 0x20(%rsp) and 0x28(%rsp).

The debugging approach

The breakthrough came from disassembling GCC's own output for a function declared with __attribute__((ms_abi)). GCC's codegen for a 5-argument call looked like: 

mov $0x2,%ecx       /* arg1 → RCX */
mov %rbx,%rdx       /* arg2 → RDX */
xor %r8d,%r8d       /* arg3 → R8 */
mov %rax,%r9        /* arg4 → R9 */
push %r12           /* arg5 → stack (push, not mov!) */
sub $0x20,%rsp      /* shadow space */
call *0xb0(%rax)    /* call */
add $0x30,%rsp      /* cleanup: 0x20 shadow + 0x8 push + 0x8 alignment */

This confirmed: the MS ABI register order is RCX, RDX, R8, R9; stack arguments are pushed (not mov'd to offset); and the cleanup accounts for shadow space plus pushed args. We adapted our wrappers to match this exact pattern.

When implementing an ABI translation layer, disassemble the compiler's own code first. GCC already knows how to do the translation correctly when you use __attribute__((ms_abi)). Use that as your reference implementation, then replace the attribute with your assembly.
